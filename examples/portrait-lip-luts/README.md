# Portrait lip LUTs (PF90021 pair)

Two original 64³ lip-colour LUT atlases plus the script that generates them.
They fill the atlas slot the lip makeup enhance effect (`PF90021`,
`lipMakeupEnhance`) reads, and they exist so that effect can run on assets this
project owns outright.

Everything here is generated by `tools/generate_luts.py` from the analytic
curves in `tools/lip_curves.py`. No vendor LUT, model, photograph or
third-party file was read, sampled or traced to produce these bytes, and there
are no neural weights in this package.

```
assets/LipsLUT.png      positive row  512x512 RGBA8  540536 bytes
assets/LipDodgeLUT.png  negative row  512x512 RGB8   696376 bytes
tools/                  standard-library Python only (no pip install)
MANIFEST.json           bytes, SHA-256s, curve parameters, measured properties
```

## Format

A 512×512 PNG holding an 8×8 grid of 64×64 tiles: one flattened 64³ colour
cube, 64 nodes per axis.

| property | value |
| --- | --- |
| tile index | `z = 8*t + s`, `px = (z & 7)*64 + x`, `py = (z >> 3)*64 + y`, top row first |
| axes | red → `+x` inside a tile, green → `+y`, blue selects the tile |
| colour types | positive row RGBA8 (alpha written 255, inert), negative row RGB8 |
| byte counts | RGBA8 atlas = **1048576** raw bytes; RGB8 atlas = 786432; the decoded 64³ RGB volume is also 786432 |
| CPU-side input | RGB8, exactly `512*512*3` bytes; a RGBA buffer is **not** accepted there |

The alpha channel matters only for the container: the loader path calls
`to_rgb8()`, so alpha never reaches the sampler. The positive row keeps the
RGBA container because that is the shape the shipped slot uses; the negative
row is RGB8.

## The two curves

Both work on Rec.709 luma with `bump(y) = 4y(1-y)`, a window that is 0 at black
and white and 1 at mid-luma, so every effect fades out exactly where the fixed
points have to hold.

**`LipsLUT` — positive: keep the lip colour, give it more chroma.**
`out = Y + gain·(c − Y)`, `gain = min(1 + 0.30·bump(Y), cube room)`. Luma is
preserved, so this is a saturation move, not a brightness move.

**`LipDodgeLUT` — negative: take the lip back toward its natural tone.**
`out = Yd + gain·(c − Y)`, `gain = min(1 − 0.35·bump(Y), cube room)`,
`Yd = Y + 0.05·bump(Y)`. Desaturates and lifts a little, which is what "dodge"
means in this slot.

"cube room" is the largest gain that keeps every channel inside `[0,1]`: the
curves clamp the *gain*, never the result, so no value is clipped into a flat
wall. A node sitting on a face of the cube therefore has no room left and is
left alone (the fully saturated primaries are exact fixed points of the
positive row).

## Measured properties (per asset, from the stored bytes)

| property | `LipsLUT` | `LipDodgeLUT` |
| --- | --- | --- |
| `(0,0,0)` and `(255,255,255)` | fixed points | fixed points |
| neutral axis (all 64 diagonal nodes) | exactly neutral | exactly neutral |
| red along `+x`, green along `+y`, blue along `+z` | non-decreasing, min step **0** (flat where the cube bound bites) | non-decreasing, min step **2** |
| the other six channel/axis pairs | not monotone (e.g. red steps −1 along `+y`); reported in the manifest, not claimed | same |
| max deviation from the identity volume | **35/255** | **64/255** |
| mean deviation | 8.78/255 | 17.80/255 |
| entries changed | 86.5% | 97.7% |

The two monotonicity rows are deliberately separate: only the channel-owning
axis is required to be non-decreasing, because boosting one channel while
leaving luma fixed must lower another one. `MANIFEST.json` records both.

`128,128,128` is exactly `128,128,128` for the positive row; the dodge row
lifts mid-grey to `140,141,141` — one byte apart per channel, because trilinear
interpolation around that point mixes nodes that are off the neutral diagonal.

## Regenerate and verify

Python 3.9+ and nothing else. Both commands work from a copy of this directory
with no other files present.

```bash
# regenerate into a scratch directory, leaving the shipped assets alone
python tools/generate_luts.py --output out/lip-luts

# both files come out byte-identical to the shipped ones
#   Unix:            cmp out/lip-luts/assets/LipsLUT.png assets/LipsLUT.png
#   Windows cmd:     fc /b out\lip-luts\assets\LipsLUT.png assets\LipsLUT.png

# verify the shipped files: container, pixel hashes, axis identity, boundaries,
# sample table, tile order, and two fresh rebuilds for determinism
python tools/verify_luts.py
```

`verify_luts.py` prints one `[PASS]`/`[FAIL]` line per check and exits non-zero
on any failure. It treats the **pixel** SHA-256 as the hard check and the PNG
file SHA-256 as informational: the container digest depends on the zlib build,
the pixels do not. On the machine that produced these files both match.

## Scope

What is verified here: the two files are valid PNGs of the shipped shapes, they
decode to the 64³ volumes described above, their pixels are deterministic, and
the format is the one this project's own decoders implement —
`VolumeLut64::from_atlas_rgb8` in `crates/portrait/src/cuda_pf90021.rs` and
`lut3d_sample` in `crates/portrait/src/kernels/face_detail.rs`. Those two were
checked against the perf-branch tree at commit `4a05bff`; that is a check of the
**format contract**, nothing more.

What is not claimed:

* **Not an entry point.** Verifying against a loader's format does not mean a
  running build reads these files. On `main`, `portrait_pf90021_input.rs` reads
  `AURORA_PF90021_LUT_POSITIVE` / `AURORA_PF90021_LUT_NEGATIVE` when set, else
  `<root_from_env()>/MakeupEnhance/{LipsLUT,LipDodgeLUT}.png`. The extra
  automatic root fallback (`portrait_makeup_wiring::makeup_asset_root`) exists
  only in the separate portrait compatibility patch, not in this PR or on
  `main`. This package does not install itself, set those variables, or wire
  the atlases into the build.
* **Not vendor pixels.** These are new curves. Nothing here reproduces,
  approximates or was fitted to any vendor asset, so no claim of matching vendor
  output is made or implied. Existing same-image fixtures baked against a fixed
  fingerprint are unaffected by this package and are not evidence about it.
* **No licensing change.** This contribution adds no separate licence and does
  not resolve the repository-wide licensing decision described in the
  [asset and licence inventory](../../ASSET-LICENSES.md).
